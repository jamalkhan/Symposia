# Presigned URLs

## Overview

A presigned URL encodes a specific storage operation — a GET, PUT, or DELETE — along with its authorization, expiry, and scope directly into a URL. The holder of the URL can execute the operation without needing a platform credential. This enables direct browser-to-storage uploads, time-limited public download links, and zero-trust file sharing without exposing long-lived credentials.

The critical property of presigned URLs is that **no live service call is required to verify them at use time**. The signature is self-contained and verified cryptographically by the gateway.

---

## Supported Operations

| Operation | Use Case |
|---|---|
| **Presigned GET** | Time-limited download link for a specific object. Share with end users, embed in email, pass to a CDN, etc. |
| **Presigned PUT** | Allow a client (e.g., a browser) to upload a file directly to the storage node without routing credentials through the application server. |
| **Presigned DELETE** | Allow a delegated party to delete a specific object without a full credential. Used sparingly; the narrow scope prevents misuse. |
| **Presigned HEAD** | Allow a client to check whether an object exists and retrieve its metadata (size, ETag, content type) without a credential. |

Presigned URLs for LIST operations are **not supported**. Enumeration access requires a proper scoped credential.

---

## URL Structure

A presigned URL is a standard HTTPS URL with authentication information embedded in query parameters:

```
https://gateway.example/my-bucket/uploads/photo.jpg
  ?X-Blob-Algorithm=HMAC-SHA256
  &X-Blob-Credential=cred_01abc%2F20260623%2Fus-east%2Fblob%2Frequest
  &X-Blob-Date=20260623T120000Z
  &X-Blob-Expires=3600
  &X-Blob-SignedHeaders=host%3Bcontent-type
  &X-Blob-Signature=a1b2c3d4...
```

This format is compatible with the AWS Signature Version 4 presigned URL format, enabling existing S3-compatible tools to generate and consume presigned URLs without modification.

---

## Expiry

- Every presigned URL carries an expiry (`X-Blob-Expires` in seconds from signing time).
- **Default expiry**: 15 minutes.
- **Maximum expiry**: 7 days (168 hours). This cap is enforced by the gateway at signature verification time regardless of what expiry the client specified.
- **Per-bucket override**: The `presigned_url_max_ttl` bucket property (see [Bucket Configuration](./bucket-configuration.md)) may set a shorter maximum for sensitive buckets, but cannot extend it beyond the platform maximum of 7 days.
- A presigned URL used after its expiry returns `403 Forbidden` with `PresignedUrlExpired`.

### HIPAA Constraint

ePHI-designated buckets enforce a maximum presigned URL TTL of **1 hour**, overriding any bucket-level or tenant-level configuration. This limit aligns with HIPAA minimum necessary access principles and prevents long-lived links to PHI from being shared outside of a controlled session. See [Security](../Platform/security.md) for the full ePHI access control model.

---

## Scope Constraints

A presigned URL is always scoped to exactly:
- One **operation** (GET, PUT, DELETE, or HEAD).
- One **bucket**.
- One **object key** (exact key only; no prefix or wildcard).

A presigned PUT may additionally scope the upload:
- **Content-Type restriction**: The URL may bind a specific expected content type. The gateway rejects the PUT if the `Content-Type` header does not match.
- **Content-Length restriction**: The URL may specify the exact expected object size. The gateway rejects uploads that differ. This prevents clients from uploading larger payloads than intended.
- **Maximum size limit**: Even without a specific `Content-Length` constraint, all presigned PUTs are subject to the platform's maximum object size (5 TB). Attempting to upload more returns `EntityTooLarge`.

### Presigned PUT and Multipart

A presigned PUT is a single-part upload only. For objects requiring multipart upload (>5 GB, or where the client wants part-level retry), the application server must generate a presigned URL for each part separately:

```
# Each UploadPart call gets its own presigned URL:
PUT /bucket/key?partNumber=1&uploadId=up_abc&X-Blob-Signature=...
PUT /bucket/key?partNumber=2&uploadId=up_abc&X-Blob-Signature=...
```

The `CompleteMultipartUpload` and `AbortMultipartUpload` calls cannot be presigned — they require a live credential (because they modify the upload session, not just a single part).

---

## Generation

Presigned URLs are generated by the application server (server-side) using a platform credential. The URL is signed using the credential's secret. Clients never see the credential itself — they receive only the signed URL.

```http
POST /credentials/{credential-id}/presign

{
  "operation": "GET",
  "bucket": "my-bucket",
  "key": "uploads/photo.jpg",
  "expires_seconds": 3600,
  "content_type": null,
  "content_length": null
}
```

Response:
```json
{
  "url": "https://gateway.example/my-bucket/uploads/photo.jpg?X-Blob-Signature=...",
  "expires_at": "2026-06-23T13:00:00Z"
}
```

All platform SDKs provide a `generatePresignedUrl()` method that wraps this signing process locally — no network call to the platform is needed to generate a URL.

---

## Signature Verification

When the gateway receives a request using a presigned URL, it:

1. Parses the `X-Blob-Credential` to identify the issuing credential.
2. Checks the revocation list for that credential (see [Multi-Tenancy and Credentials](./multi-tenancy-and-credentials.md)). A revoked credential invalidates all presigned URLs it signed, immediately.
3. Verifies the `X-Blob-Expires` has not passed.
4. Recomputes the signature over the canonical request and compares it to `X-Blob-Signature`. Any mismatch (URL tampering, wrong operation, wrong key) returns `403 Forbidden` with `InvalidPresignedUrl`.
5. Checks the bucket's `public_access_block` setting. If set, presigned URLs are disabled regardless of signature validity.

---

## Revocation

Unlike regular credential revocations (which propagate within 60 seconds), presigned URL revocation has an important nuance:

- **Revoking the issuing credential** immediately invalidates all presigned URLs signed by that credential. This is the primary revocation mechanism.
- There is **no per-URL revocation** — a URL cannot be invalidated individually without revoking the credential that signed it.
- This is a deliberate architectural simplicity. If fine-grained URL revocation is required, use separate short-lived credentials per URL context.

---

## Audit Logging

Every use of a presigned URL is recorded in the audit log with:
- The credential that signed the URL.
- The operation, bucket, and key.
- The source IP of the caller.
- Whether the request succeeded or failed, and why.

The log records the URL use even if the URL is expired or invalid at time of use. This allows tracking of leaked or reused URLs.

---

## Public Access and Presigned URL Interaction

| Bucket Setting | Effect on Presigned URLs |
|---|---|
| `public_access: none` (default) | Presigned URLs work normally. |
| `public_access: read` | Public GET access does not require a presigned URL, but presigned GET URLs still work and are tracked. |
| `public_access_block: true` | All presigned URLs are disabled. Requests using presigned URLs return `PublicAccessBlocked`. |
| ePHI-designated bucket | Presigned URLs are allowed but TTL is capped at 1 hour; no public access mode is permitted. |
